## Етап S9 — Наскрізні сценарії та повний прогін

**Мета:** кожен сценарій аномалії доведено в усіх трьох сигналах автоматичним тестом. Є тест зупинки `worker`. Одна команда `make verify` піднімає стенд із нуля й проганяє все.

**Залежить від:** S8. Перевірка: `make lint unit e2e` зелені, `make check-ports` друкує `PORTS OK`.

**Файли:**

- створити `tests/e2e/test_s09_scenarios.py`, `tests/outage/test_s09_worker_outage.py`, `scripts/verify.sh`;
- змінити `Makefile`, `docker-compose.yml`, `tests/outage/conftest.py`, `tests/e2e/helpers.py`.

**Вимоги:**

1. **`test_s09_scenarios.py`** — по одному повільному тесту на сценарій `slow_queries`, `lock_contention`, `deadlocks`, `failures`. Кожен тест:
   1. чекає, доки всі алерти стануть `inactive`, а черга спорожніє;
   2. запамʼятовує момент початку й вмикає сценарій фікстурою `scenario(name)`;
   3. не пізніше ніж за 120 с дочікується стану `firing` усіх обовʼязкових алертів сценарію з §11;
   4. перевіряє метрики сценарію (таблиця нижче);
   5. знаходить докази в Loki й Tempo запитами з §11, обмеженими часом від початку сценарію;
   6. після виходу з фікстури дочікується: усі сім алертів `inactive` не пізніше ніж за 150 с, `messages_ready` менше 50, `check_invariants()` порожній.

   | Сценарій | Перевірка метрик під час сценарію |
   |---|---|
   | `slow_queries` | p95 `bank_transfer_processing_seconds` за хвилину більший за 0,5 с; `rabbitmq_queue_messages_ready` перевищує 200 |
   | `lock_contention` | `max_over_time(bank_db_lock_waiters[1m])` не менше 1; `bank_db_longest_transaction_seconds` перевищує 0,3 |
   | `deadlocks` | приріст `pg_stat_database_deadlocks{datname="bank"}` від початку — не менше 3; `bank_transfer_retries_total{reason="deadlock"}` зростає |
   | `failures` | частка `failed` за хвилину більша за 0,2; швидкість `pg_stat_database_xact_rollback` більша, ніж до сценарію |

2. **Тест ланцюжка «метрика → лог → трейс».** Для одного переказу зі статусом `failed`, створеного під час сценарію `failures`: рядок `transfer_failed` у Loki знайдено за `transfer_id`; його `trace_id` відкривається в Tempo; у трейсі є спан `worker.process_transfer` з тим самим `bank.transfer_id`.
3. **Тест зупинки `worker`** — три запуски pytest, між якими `make` зупиняє й запускає контейнер. Стан між запусками зберігається у файлі на томі `tests_state`, змонтованому в контейнер `tests` у `/state` (том додається в `docker-compose.yml`).
   - `test_phase0_baseline`: поставити генератор на паузу, дочекатися порожньої черги, записати у файл кількість рядків `transfers` і значення `bank_generator_operations_total{operation="transfer",result="ok"}`, зняти паузу.
   - (`make` виконує `docker compose stop worker`.)
   - `test_phase1_backlog`: `up{job="worker"}` стає 0 не пізніше ніж за 30 с; `messages_ready` перевищує 200 не пізніше ніж за 60 с; `QueueBacklog` і `ServiceDown` стають `firing` не пізніше ніж за 120 с.
   - (`make` виконує `docker compose start worker`.)
   - `test_phase2_recovery`: `messages_ready` менше 50 не пізніше ніж за 120 с; поставити генератор на паузу, дочекатися порожньої черги й нуля в `bank_worker_in_flight`; приріст кількості рядків `transfers` точно дорівнює приросту лічильника генератора (жоден переказ не загублено); `check_invariants()` порожній; зняти паузу; усі алерти `inactive` не пізніше ніж за 150 с.
4. **`make outage-test`** виконує ці три фази по черзі. Якщо будь-яка фаза впала — `worker` усе одно запускається, генератор знімається з паузи, а ціль завершується з помилкою.
5. **`scripts/verify.sh`** і ціль `make verify`. Кроки по черзі, кожен із заміром часу:
   1. `make clean`;
   2. `scripts/check_images.sh`;
   3. `make up` (базовий режим);
   4. `make check-ports`;
   5. `make lint`;
   6. `make unit`;
   7. `make e2e`;
   8. `make outage-test`;
   9. `scripts/check_json_logs.sh` для `worker`, `generator`, `auth`;
   10. підсумковий стан: сценарій `normal`, генератор працює, активних алертів немає, `RestartCount` кожного контейнера дорівнює 0.

   Наприкінці — таблиця «крок, тривалість, результат» і останній рядок `VERIFY OK`. Якщо крок упав: назва кроку, `docker compose ps`, останні 40 рядків логів контейнерів не в стані `running`/`healthy`, ненульовий код. Стенд після прогону лишається запущеним.
6. **Дозволене підлаштування.** Якщо сигнал сценарію нестабільний (алерт спрацьовує не в кожному з трьох прогонів поспіль), на цьому етапі можна змінити числові параметри сценаріїв у §6.6 (`lock_gap_ms`, `sleep_ms`, кількість «гарячих» рахунків, частка великих сум) і пороги та `for` правил у §6.10. Зміна вноситься одночасно в `docs/00-common.md`, код, правила й тести окремим комітом `tune: <що і чому>` і записується в журнал. Назви, структура й решта контракту лишаються незмінними. Спершу шукай помилку в реалізації: підлаштування — останній засіб.

**Поза межами етапу:** нові сценарії, нові метрики чи дашборди, навантажувальне тестування понад описане, зміна логіки сервісів (крім виправлення знайдених дефектів).

**Acceptance criteria:**

- **S9-AC1.** `test_s09_ac1_slow_queries` зелений тричі поспіль.
- **S9-AC2.** `test_s09_ac2_lock_contention` зелений тричі поспіль.
- **S9-AC3.** `test_s09_ac3_deadlocks` зелений тричі поспіль.
- **S9-AC4.** `test_s09_ac4_failures` зелений тричі поспіль.
- **S9-AC5.** Тест ланцюжка `test_s09_ac5_metric_log_trace_chain` зелений.
- **S9-AC6.** `make outage-test` зелений; після нього `worker` у стані `healthy`, генератор працює.
- **S9-AC7.** `make verify` завершується рядком `VERIFY OK` двічі поспіль; кожен прогін триває не довше 30 хвилин.
- **S9-AC8.** `make e2e` зелений двічі поспіль на тому самому живому стенді без `make clean` між прогонами.
- **S9-AC9.** Холодний старт: `make clean && make up` із уже завантаженими образами триває не довше 5 хвилин, і всі контейнери — `running` або `healthy`.
- **S9-AC10.** Витримка: після 10 хвилин роботи в режимі `normal` запит `count_over_time(ALERTS{alertstate="firing"}[8m])` порожній; `RestartCount` кожного контейнера — 0; `messages_ready` менше 50; сумарна памʼять контейнерів за `docker stats --no-stream` менша за 4 ГіБ; `check_invariants()` порожній.
- **S9-AC11.** Жоден тест у `tests/` не містить `time.sleep` поза `wait_until` (перевірка: `grep -rn "time.sleep" tests/` показує лише `helpers.py`).

**Перевірка:**

```bash
make up
for i in 1 2 3; do make e2e K=s09 || break; done
make outage-test && docker compose ps worker
make e2e && make e2e
time (make clean && make up)
make verify && make verify
docker stats --no-stream --format 'table {{.Name}}\t{{.MemUsage}}'
grep -rn "time.sleep" tests/
```

**Ручна перевірка:** увійти як `admin`, відкрити поруч `/control/` та оглядовий дашборд. По черзі ввімкнути чотири сценарії з автоповерненням 120 с і для кожного переконатися, що: показники на огляді змінюються; у таблиці «Активні алерти» зʼявляється очікуваний алерт; після повернення все стає зеленим.
