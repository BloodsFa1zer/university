# Як перевірити BankMonitor самостійно

Покрокова перевірка всього, що вміє система: спершу автоматично, потім руками в браузері. На все разом піде ≈1 година, з них 30 хвилин — автоматичний прогін, коли можна займатися іншим.

## 0. Підготовка (5 хв)

1. Запусти Docker Desktop; у Settings → Resources дай контейнерам щонайменше 6 ГБ памʼяті.
2. Перевір, що порт 8080 вільний: `lsof -i :8080` нічого не показує. Якщо зайнятий — у `.env` (зʼявиться після першого `make`) постав `GATEWAY_PORT=8081` і далі всюди замість 8080 пиши 8081.
3. У теці проєкту:

```bash
make up
```

Перший раз — кілька хвилин (завантаження образів і збірка). Команда повертається, коли все готово.

```bash
docker compose ps -a
```

Усі дванадцять сервісів мають бути `running` / `healthy`, а `grafana-init` — `Exited (0)` (він одноразовий).

## 1. Автоматична перевірка всього (30 хв, можна не дивитися)

```bash
make verify
```

Скрипт з нуля піднімає стенд і проганяє все: перевірку образів, портів, лінтер, юніт-тести, ≈250 наскрізних тестів на живому стенді, тест зупинки worker, перевірку логів. Наприкінці — таблиця кроків з часом і рядок **`VERIFY OK`**. Якщо щось упало — скрипт покаже, на якому кроці, і логи контейнерів.

Окремі частини, якщо хочеш швидше:

| Команда | Час | Що перевіряє |
|---|---|---|
| `make lint unit` | 30 с | стиль коду й ≈150 юніт-тестів |
| `make e2e` | ≈18 хв | усі наскрізні тести (стенд має бути запущений) |
| `make e2e K=s04` | 10 с | лише тести одного етапу, тут — авторизацію |
| `make outage-test` | ≈1,5 хв | зупинка й запуск worker без втрат |
| `make check-ports` | 1 с | назовні відкритий лише порт 8080 |

## 2. Авторизація (пункт 7 завдання, 5 хв)

1. Відкрий у приватному вікні <http://localhost:8080/control/> — має зʼявитися форма «Вхід до BankMonitor».
2. Введи `admin` і неправильний пароль → «Невірний логін або пароль», логін лишився в полі.
3. Введи `admin` / `admin12345` → відкривається сторінка «Керування навантаженням».
4. Відкрий <http://localhost:8080/auth/logout> → знову форма входу.
5. Увійди як `viewer` / `viewer12345` → відкривається Grafana; тепер <http://localhost:8080/control/> → `403 Forbidden`, а <http://localhost:8080/prometheus/> → теж `403`.
6. З терміналу: `curl -i http://localhost:8080/control/api/state` → `401` і `{"detail":"Not authenticated"}`.

## 3. Дашборди Grafana (пункти 1–4, 10 хв)

Увійди як `viewer` і відкрий <http://localhost:8080/grafana/> — одразу відкриється «BankMonitor — огляд». Угорі є посилання на інші дашборди.

| Дашборд | Що має бути |
|---|---|
| BankMonitor — огляд | «Сервіси в роботі»: 10 з 10 (усі цілі Prometheus), ≈45 транзакцій БД і ≈14 переказів за секунду, відмов 0 %, «Активних алертів немає» |
| PostgreSQL | зʼєднання, транзакції, рядки, кеш, розмір бази, таблиця «Найважчі запити» з текстом SQL |
| Застосунок: перекази | операції генератора, перекази за статусом, час обробки, входи, HTTP-запити |
| RabbitMQ | черги `transfers.requested` і `transfers.dead`, 4 споживачі |
| Логи | рядки всіх сервісів, фільтр «Сервіс» і поле «Пошук» |
| Трейси | таблиці трейсів (наповнюються під час сценаріїв) |

Ніде не повинно бути «No data».

Prometheus (увійди як `admin`): <http://localhost:8080/prometheus/targets> — усі цілі зелені `UP`; <http://localhost:8080/prometheus/alerts> — 7 правил `INACTIVE`.

## 4. Черга RabbitMQ (пункт 9, 5 хв)

1. Відкрий дашборд «RabbitMQ».
2. У терміналі: `docker compose stop worker` — графік «Повідомлення в чергах» росте; за ≈1 хв на огляді зʼявляться алерти `QueueBacklog` і `ServiceDown`.
3. `docker compose start worker` — черга за кілька секунд падає до нуля, алерти гаснуть. Жодна заявка не втрачена (це автоматично доводить `make outage-test`).

## 5. Аномалії: метрики → логи → трейси (пункти 5–6, 15 хв)

Увійди як `admin`, відкрий поруч <http://localhost:8080/control/> і огляд. На сторінці керування кожен сценарій вмикається кнопкою й сам повертається через 120 с.

| Сценарій | Що побачити |
|---|---|
| Повільні запити | огляд: «p95 обробки переказу» > 0,8 с, черга росте, алерти TransferProcessingSlow і QueueBacklog; «Трейси» → «Повільні перекази» → відкрий трейс → довгий SQL-спан `pg_sleep` |
| Конкуренція за блокування | «PostgreSQL» → «Сесії, що чекають блокування» > 0, алерт LockWaiters; «Логи» → панель PostgreSQL → рядки «still waiting for» |
| Взаємні блокування | огляд → «Взаємних блокувань за хвилину» > 0, алерт DeadlocksDetected; «Логи» → «deadlock detected»; «Трейси» → «Перекази з повторами» → спан з подією `deadlock_retry` |
| Масові відмови | огляд → «Частка відмов» ≈ 50 %, алерт TransferFailureRatioHigh; «Логи» → «Логи сервісів», у «Пошук» введи `transfer_failed` |

Переходи між сигналами:

- **метрика → трейс:** на «Застосунок: перекази» на графіку «Час обробки: p50, p95, p99» є маленькі ромбики (exemplars); наведи на ромбик — у підказці є `trace_id` і посилання на трейс у Tempo;
- **трейс → логи:** у відкритому трейсі розгорни спан і натисни «Logs for this trace» — відкриється рядок worker `transfer_completed` з цим `trace_id` (якщо трейс зовсім свіжий і рядків worker ще немає — через 10–20 с натисни «Run query»);
- **лог → трейс:** у Explore → Loki виконай `{service="worker"} | json | event="transfer_completed"`, розгорни рядок → кнопка «Відкрити трейс» біля `trace_id`.

Наприкінці на сторінці керування натисни «Звичайний режим».

## 6. Команди з терміналу (5 хв)

```bash
make scenario NAME=deadlocks TTL=60
```

```bash
make logs S=worker
```

```bash
scripts/check_json_logs.sh worker
```

```bash
make up-dev
```

Після `make up-dev` сервіси доступні напряму на `127.0.0.1` (таблиця портів — у README), наприклад інтерфейс RabbitMQ <http://127.0.0.1:15672> (логін і пароль — `RABBITMQ_DEFAULT_USER` і `RABBITMQ_DEFAULT_PASS` з `.env`). Повернутися: `make down && make up`.

## 7. Завершення

```bash
make down
```

Зупиняє все, дані зберігаються. `make clean` — зупинити й видалити всі дані.
